# 🔎 Full Blueprint & Automation Audit — 2026-10-11

This audit was completed before the current repository revision was approved. The goal was not merely to confirm that the YAML looked reasonable, but to review logic, documentation, privacy, validation coverage, and failure behavior.

## Audit Scope

Every public Blueprint in the repository was reviewed, compared with the reusable automation/script patterns that the project is intended to represent, and converted into a public form without private home entity IDs or device-specific configuration.

The repository currently targets **9 Blueprints**:

1. Smart Irrigation.
2. Long-running Water Safety.
3. Outdoor Lights — Dusk to Dawn.
4. Outdoor Light — Abnormal State Alert.
5. Zone Exit Notification.
6. Quran Sunrise & Sunset via Music Assistant.
7. Available Updates — Daily Summary.
8. Quran Safe Toggle Script.
9. Manual Irrigation — Safe Timed Run.

## Key Findings and Fixes

### 1. Smart Irrigation Needed Stronger Hardware Safety Logic

The earlier design allowed `mode: restart` around water-control logic and did not detect every early single-valve OFF transition cleanly.

The hardened design now uses:

- `mode: single`.
- Blocking when a selected valve is already ON before a scheduled run.
- Startup verification for every selected valve.
- Early OFF detection for any selected valve.
- Final OFF verification.
- Failure notifications instead of assuming success.

### 2. Flow Validation Needed to Be Per Sensor

Checking only the combined flow can hide a failed branch: one sensor may report zero while another reports enough flow to keep the total above zero.

The current logic validates **every selected flow sensor**. When no-flow protection is enabled, any selected sensor that is unavailable, non-numeric, zero, or negative fails the check and causes a shutdown.

### 3. Repeat Scheduling Needed Midnight-safe Intervals

A simple hour modulo can produce uneven behavior across midnight when the interval does not divide 24 evenly.

Repeat-mode choices are therefore restricted to:

`1, 2, 3, 4, 6, 8, 12, 24`

These values divide 24 hours cleanly and remain anchored to local midnight.

### 4. Outdoor Abnormal-state Alert Needed Trigger-time Variables

Template triggers are evaluated when Home Assistant attaches and tracks the trigger. Values required by the trigger must therefore be available at trigger-rendering time.

The corrected Blueprint uses:

- `trigger_variables` for values required by the template trigger.
- `variables` for action-time logic.

A static validation rule was added so this class of undefined-variable mistake is detected automatically in the future.

### 5. Dusk-to-Dawn Needed Verification After Retry

The lighting automation now follows this sequence:

1. Send the requested light command.
2. Verify the resulting state.
3. Wait five seconds and retry once if needed.
4. Verify again.
5. Create persistent and mobile failure notifications if the second verification fails.

There is intentionally no startup force-sync so a Home Assistant restart does not automatically reverse a manual lighting decision.

### 6. Water Safety Needed Unique Notification Action IDs

Stop and Keep buttons now use IDs derived from `context.id` for every automation run.

The watchdog also includes:

- A five-minute periodic fallback.
- A Home Assistant startup fallback.
- OFF-state verification after Stop.
- Critical failure notification when shutdown cannot be confirmed.
- A configurable notification tag.

### 7. Quran Playback Needed a Single Playback Layer

The Quran Blueprints restrict their player selector to:

`integration: music_assistant`

They do not use native Apple TV, native Google Cast, YouTube, or `media_extractor` as the public playback architecture.

Playback is considered successful only when:

- `state == playing`
- and `media_content_id == requested URI`

### 8. Quran Toggle Needed Verification for Stop and Resume

The toggle script no longer assumes that sending Stop or Resume means the operation succeeded.

Each branch now waits for the expected resulting state and reports failure when that result cannot be confirmed within the timeout.

### 9. Available Updates Should Not Infer Priority from Names

Classifying update importance with regular expressions over `friendly_name` is fragile across languages and integrations.

The new Blueprint lets users explicitly select **Priority Update Entities**. Every remaining available update is grouped under Other.

### 10. Manual Irrigation Needed a Reusable Safe Script

The reusable Manual Irrigation Script now:

- Requests a duration for each run.
- Refuses to take over a selected valve that is already ON when blocking is enabled.
- Verifies startup.
- Validates selected flow sensors.
- Detects early shutdown.
- Verifies final OFF state.
- Recommends the independent Water Safety Watchdog as a second safety layer.

### 11. HACS Metadata Was Misleading

This repository is a multi-Blueprint collection, not a supported HACS repository type for the content being published.

The misleading `hacs.json` file was removed so installation instructions correctly point users to Home Assistant Blueprint import.

### 12. Unrelated Non-Home-Assistant Content Was Removed

An unrelated service-request form was removed from the repository so the project remains focused on Home Assistant content and does not mix unrelated organization-specific material into the public tree.

### 13. Validation Caught an Invalid SVG

The first validation run found that the water-safety SVG contained an unescaped `&`, making it invalid XML.

The artwork was corrected and the SVG/XML check remains part of the permanent validation gate.

## Documentation and Artwork Gate

Every Blueprint must now have:

- A unique dedicated SVG image.
- A dedicated detailed guide.
- Input documentation.
- A step-by-step execution explanation.
- Failure behavior.
- Restart/reload limitations when relevant.
- A safe live-test checklist.
- A direct import URL.

The static validator enforces this policy for every Blueprint in the validation map.

## What “Validated” Means

The repository uses two levels of verification.

### Level 1 — Automatically Verifiable

The CI can prove that:

- YAML and XML parse successfully.
- Blueprint metadata and `!input` references are valid under repository rules.
- Every documented local link points to an existing file.
- Every Blueprint can be instantiated in the Home Assistant test configuration.
- Home Assistant `check_config` succeeds on the tested Core version.
- Every Blueprint has the required dedicated documentation and artwork.
- Known private-home identifiers are not present in public text files.

### Level 2 — Requires Real Hardware

Repository CI cannot prove:

- That a physical water valve closed mechanically.
- That a Zigbee or Wi-Fi command reached a device every time.
- That an AirPlay or Cast player produced audible sound.
- That a GPS tracker updated at a specific real-world moment.
- That every firmware version reports state identically.

For that reason, hardware-facing guides include live-test checklists and do not claim a physical guarantee that CI cannot establish.
